# 首次使用与一次内容确认

## 用户入口

第一次只展示以下选择，无需先完成偏好问卷：

1. 直接用我们的模板。
2. 选择模板的部分条目。
3. 啥也不要，自己迭代。

可选第 4 项：基于 Agent 已授权的记忆和使用记录提出候选规则。用户已有明确说明时直接导入，避免重复选择。

选 1：默认预览 `scenario/reviewed-project@1.0.0`，明确其完整分析、列表优先及中文维护偏好；用户倾向简明表达时展示 `scenario/concise-project@1.0.0`。两者各包含 27 条规则。以工具 catalog 为准，默认只作用于预览，用户确认前不生效。需要精细搭配时再展开五个系列，避免首次展示全部十个变体。不能把“全部模板”理解为同时采用互斥偏好；先说明同系列限制，集中解决实际冲突。

选 2：完整展示选定模板，收集一次保留/排除/修改清单。保留模板引用并用 `null` override 排除单条；如改为直接引用原子规则，说明 `Profile.templates` 为空时 updates 只追踪这些直接规则，模板映射材料不等于模板升级关系。

选 3：保持占位正文与已有规则，不建立空 Profile、锁或候选，不继续提问。已有规则项目选择此项只表示跳过本次配置，不删除原规则。以后用户提出规则或反馈时再提交候选。

选 4：先说明 Agent 当前拥有的已授权记忆范围。候选附内容、证据、适用范围、明确要求或推测标记和冲突；个人事实与一次性要求保留其原职责。没有记录时明确说明，不编造使用历史。用户批准前只保留私有候选；不扫描其他项目、不上传记录、不自动计成熟度或晋升。记忆检索与建议生成由 Agent 完成，CLI 不读取客户端记忆，也不推断行为规则。

第一次展示完整规则预览时，提示：“这是一版可以开始使用的规则。后续可以根据实际任务和反馈增删、调整或换模板，无需现在一次想全。我们鼓励先使用再迭代；每次修改会先展示变化，确认后保存为新版本。”只提示一次，不添加偏好访谈或新的确认轮次。用户当前不确定的条目可以先排除；已经确认的规则在新版本批准前继续有效。初次规则配置的迭代不降低具体任务的交付承诺。

## 预览先于正式保存

以下命令由 Agent 执行，用户只审阅规则内容。项目目录必须已经存在；所有个人材料只放在该项目指定的私有位置。项目治理应忽略候选与中间目录；vcs:none 的项目仅说明忽略配置，不声称已有 Git 收录行为。

直接用模板的 Profile 预览：

```bash
python3 plugins/opinion-manager/runtime/opinion_manager.py profile   --project /path/to/project --catalog plugins/opinion-manager/catalog   --id private.my-opinion --version 1.0.0   --template scenario/reviewed-project@1.0.0 --output json
```

保存该输出的 `profile` 对象到项目私有候选 JSON，保留完整预览回执；禁止将整个命令结果作为 Profile。候选文件仅用于审阅，正式 `.opinion/profiles/.../versions/1.0.0.json` 此时不存在。

```bash
python3 plugins/opinion-manager/runtime/opinion_manager.py compose   --project /path/to/project --profile /path/to/private-preview/profile.json   --output json
```

检查 `unresolved` 为空、`blocked` 为空，且两份预览 `content` 完全一致。集中展示完整正文、有效/排除规则、来源版本、个人修改、差异与拟保存文件，提供完整 Profile 和锁 JSON 的可读入口。用户一次确认这个结果后，Agent 记录两份真实指纹。

写入前重新执行相同两份预览，检查两项指纹及内容仍与批准结果一致。相同内容不用再次请求确认；任何变化须重新展示。先在原 Profile 命令上追加 `--apply --confirm <Profile预览指纹>`，再将 compose 路径换成正式 Profile，在原 compose 参数上追加 `--apply --confirm <compose预览指纹>`。两项指纹不能互换。Profile 保存不会修改正文和锁，因此在目标未变化时 compose 指纹仍有效；工具再次检查当前状态。写后完整读取 Profile、正文与锁，核对预览并运行 verify。

用户确认可涵盖整个内容包；CLI 两次写入仍各自核验真实指纹。保存 Profile、正文、锁并非一次系统事务；若后一步失败，保留真实已写入状态，禁止声称完成或覆盖文件回滚，按版本契约修复。旧 Profile/锁和正文渲染格式保持兼容。

## 冲突与个人编辑

使用模板的部分条目时优先保留模板关系。平行偏好不要自动折中；列出可读标题、全文和冲突位置，一次让用户选择保留一边、按场景区分或确认个人改写。个人改写只属于用户环境；转公开模板另做逐文件审批。

人工编辑项目先完整读回当前正文并纳入新 Profile，展示完整差异，使用真实当前文件指纹 `--accept-current`。预览显示保护阻断时不能以“用户已经确认入口”为由绕过。升级使用精确目标版本，保留所有个人修改；先查看 updates，再预览新版本，采用同一内容确认流程。

## 客户端与项目目录

新项目优先让用户选择容易找到的可见目录，例如用户自己命名的 Documents 子目录。需要打开隐藏目录时，macOS 文件选择器可用 ⌘⇧G 输入完整路径，或 ⌘⇧. 显示隐藏项；隐藏测试目录不应成为新用户前提。

插件文件安装、项目 doctor 与桌面 Skill 发现分别核验。新 Session 按实际提供的 Skill 清单记录来源及版本；同名包并存时明确选择来源，禁止依据文件存在声称已发现。源码安装命令不能证明桌面缓存自动刷新；通过当前客户端的原生插件安装/启用流程完成加载。

升级保留配置和恢复副本，未经用户授权不删除或停用旧来源。正式使用时建议一次只保留一个明确选择的 Opinion Manager provider；如果仍有多来源，新 Session 需报告当前实际加载来源。CLI 的可用命令以当前客户端帮助为准，禁止手工修改其管理的缓存或猜测未支持的命令。
